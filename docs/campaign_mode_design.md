# 独立跑团模式产品与架构设计

状态：R1 已落地并完成自动化与真实界面验收；本文同时保留后续扩展边界

日期：2026-08-03（北京时间）

本文只记录跑团模式的产品边界、当前行为和后续扩展方向；公开版不包含个人交接记录或真实 Provider 凭据。

## 1. 结论

跑团不应被实现成“群聊加一个 GM 提示词”，而应成为 TavernDesk 左侧栏中的独立产品入口和独立数据域。

第一版已经完成一个闭环：

> GM 建立场景 → USER 与 0–4 个 AI 玩家提交行动 → GM 统一裁决 → 保存并进入下一轮。

R1 当前行为：

- 仅做“轮次制、手动推进”，不自动无限续写；
- 用三个预设覆盖协作、竞争和严格顺序，不开放任意规则组合器；
- 所有模式都冻结世界事实；只有“尚未裁决的玩家提议”是否互相可见因预设而不同；
- 角色卡与可选记忆在创建跑团时复制为只读快照；
- 普通聊天、角色长期记忆和跑团数据物理隔离，默认绝不回写；
- GM 是唯一可推进世界事实的人；
- 每个席位的一次生成都有独立缓存和终态；失败、截断或被停止的内容不会进入 GM 裁决；
- 秘密同投在同一冻结上下文下有限并发；协作圆桌和严格先攻按可见性要求顺序执行；
- AI 正常完成的行动自动锁定；技术失败可重试且不覆盖旧尝试；
- USER 与 AI 的每条成功锁定行动都在同一事件内原子附加一枚可信 `1d20`，骰点沿用行动可见性；额外的 `NdM±K` 仍作为独立公开骰点工具；
- GM 可以推进剧情、环境与 NPC，但不能替玩家补写新台词、心理、决定、反应或下一步；AI GM 裁定必须以 `【下一轮评定参考】` 收尾，否则保留失败原文且不推进回合；
- 不实现真正实时循环、通用多 Agent 框架、知识图谱、向量记忆、复杂规则引擎或地图系统。

这既满足独立跑团的本质要求，也不会把当前群聊、普通消息和记忆代码改造成一个到处需要判断可见性的“大框架”。

第一性原则下，R1 只回答四个问题：

1. 当前世界事实是什么；
2. 哪个席位现在可以行动；
3. 谁能看到尚未裁决的行动；
4. 哪些行动已经完整、可被 GM 安全裁决。

模型数量、Provider、并发和界面动画都只能附着在这四个事实之上，不能反过来成为数据结构的中心。

## 2. 调查输入与取舍

### 2.1 TavernDesk 当前可复用能力

依据 README 与定向代码核对，当前已经具备：

- 角色卡、书架、Persona 与世界书；
- 群聊成员和接力顺序；
- Grok CLI ACP，以及 OpenRouter、硅基流动、DeepSeek 官方 API、LM Studio 共用的 OpenAI-compatible Provider 边界；
- 可并行的会话级生成、流式事件和取消；
- SQLite、稳定消息顺序、记忆草稿与上下文检查；
- 上下文超限时阻止发送，不静默裁剪；
- 记忆正文必须经用户确认后才覆盖。

跑团应复用这些基础能力，但不应复用普通聊天的持久化语义。

### 2.2 外部参考站点的有效启发

观察的 ISEKAI ZERO 火影故事线页面：

<https://www.isekaizero.ai/storylines/6a66ef216f65cf180ec3c7e5?src=discovery>

它把一个故事产品拆成世界简介、角色阵容、开场情景、隐藏提示、指南、提醒和 Token 统计。这说明“故事线/战役”应是独立对象，而不只是某个角色的聊天。

同时，该页面显示预估总计约 29k Token，其中角色资料约 22k；隐藏指南存在大量语义重复的世界一致性、认知、行为、对白和叙述约束。TavernDesk 不应复制这种依靠超长提示词维持一致性的方式，应把规则、事实、可见知识和近期叙事分开管理。

### 2.3 Grok 反证讨论

Grok 的第一次审查确认了五项硬边界：

1. 跑团会话隔离；
2. 每个参与者的可见性隔离；
3. 角色卡与导入记忆的只读快照；
4. GM 单写世界状态；
5. 同轮输入快照冻结。

Grok 最初建议扩展现有 `messages` 和 `memory_banks`。补充实际 schema 后再次审查，它同意独立跑团表更符合最小修改和隔离原则，因为现有普通聊天的 FTS、删除、分支、导入导出均没有回合、私密收件人和 GM-only 语义。

## 3. 产品定义

### 3.1 名称

工作名称：`跑团`

数据实体名称：`Campaign`（战役/跑团）

左侧栏使用独立入口，不挂在“聊天”或“角色”的二级页面内。

### 3.2 参与者

- `GM`：可由 AI 或 USER 担任；负责场景、NPC、规则裁定、世界变化与下一轮提示。USER 担任 GM 时不产生 GM 模型请求。
- `USER`：真人玩家，可使用当前 Persona，也可为本跑团建立独立玩家设定。
- `AI Player`：0–4 个；从书架选择角色卡，像玩家一样提交行动和对白，不负责裁决世界。只要 USER 是玩家，0 个 AI 也可以开局。
- `NPC`：MVP 全部由 GM 控制，不为每个 NPC 创建独立模型席位。

### 3.3 核心体验边界

GM 负责“世界如何回应”，玩家只负责“我想做什么”。

AI 玩家不得：

- 宣布自己的行动已经成功；
- 替 GM 改写世界状态；
- 代表 USER 决定、说话或思考；
-读取其他玩家私有记忆或 GM 隐藏信息。

GM 不得：

- 替 USER 或 AI 玩家决定主观行动；
-把未公开秘密写进公共叙事；
-在同一轮裁决两次；
-绕过冻结快照读取尚未提交的后续信息。

## 4. 数据与记忆隔离

### 4.1 四层信息

| 层 | 内容 | 谁能读取 | 是否回写普通聊天 |
|---|---|---|---|
| 角色源快照 | 角色卡、Persona、可选初始记忆 | 对应玩家与 GM | 否 |
| 公共事件 | GM 叙事、公开对白、公开行动与裁决 | 全体 | 否 |
| 私有信息 | 单个玩家获得的秘密、私聊、个人跑团记忆 | 该玩家与 GM | 否 |
| GM 状态 | 世界摘要、未公开事实、时间线、待触发事件 | 仅 GM；用户可在导演视角查看 | 否 |

### 4.2 快照规则

创建跑团时：

- 选择角色卡后，角色核心字段复制进跑团快照；
- 默认不导入该角色的普通聊天记忆；
- 用户显式勾选后，才复制当时的记忆正文；
- 快照记录来源 ID、创建时间和内容哈希；
- 创建后，书架角色卡或普通记忆的修改不影响已开始的跑团；
- 跑团产生的任何记忆默认不回写角色卡或普通记忆。

未来若需要“把跑团经历带回角色”，只能生成用户可编辑的合并草稿，不能直接覆盖。

### 4.3 角色内嵌世界书

推荐默认仅导入角色人格与经历，不自动把角色卡内嵌世界书并入战役世界。

例如“雪乃、海梦穿越到火影”时：

- 火影规则由战役世界提供；
- 雪乃与海梦的性格、关系和可选原世界记忆来自角色快照；
- 她们原世界的世界书只有在用户明确选择“携带原世界知识”时进入各自私有上下文；
- 角色内嵌世界书不得覆盖 GM 的战役规则。

## 5. 最小持久化模型

R1 新增四张表，不修改普通 `conversations`、`messages` 和 `memory_banks` 的语义。其中一张保存可复用剧本模板，另外三张保存每一局独立跑团。

### 5.1 `campaign_scenarios`

保存：

- 剧本标题、摘要、世界设定和公开规则；
- 只在开局准备时展示的大厅说明；
- 供 GM 使用的开场设定；
- 只归档、不送入当前跑团上下文的旧示例；
- 原始卡片 JSON、源文件路径与导入报告。

导入角色卡式剧本时，`first_mes` 映射为大厅说明，`mes_example` 映射为旧示例档案。两者都不会成为角色首次发言或当前事件。

### 5.2 `campaigns`

保存：

- 标题、状态、创建/更新时间；
- 当前轮号、当前阶段、冻结事件序号与流程预设；
- 世界设定与规则文本；
- GM Provider/模型与请求参数；
- 玩家默认 Provider/模型与请求参数；
- GM 世界摘要与状态版本；
- 上下文预算与自动推进设置。

### 5.3 `campaign_participants`

保存：

- USER/AI 类型、顺序、启用状态；
- 书架角色来源 ID；
- 角色卡只读快照；
- Persona 快照；
- 可选导入记忆快照；
- 本跑团专属记忆正文；
- 可选的单席位模型覆盖。

GM 配置保存在 `campaigns`，不必伪装成普通参与者。

### 5.4 `campaign_events`

作为跑团唯一事件流，保存：

- 稳定 `sequence_no` 与 `round_no`；
- 事件类型：GM 开场、玩家意图、GM 裁决、私有投递、状态增量、系统状态；
- actor 与可选 recipient；
- 可见性：`Public`、`Private`、`GmOnly`；
- 正文、结构化尾部、冻结序号、尝试编号、生成状态、结束原因与操作 ID；
- 是否被撤销或替换。

### 5.5 为什么 R1 不建 `campaign_rounds`

当前轮号、阶段和冻结序号可放在 `campaigns`；历史事件自带 `round_no`。对“单轮手动推进”的第一版足够。

R1 的单席位缓存、失败和重试直接用带 `operation_id` 的事件表达；重试新建一次尝试，不覆盖旧尝试，因此不需要第五张表。

秘密同投的有限并发只存在于一次显式执行中；进程退出后的未完成请求落为可重试终态，不尝试恢复活着的 barrier。只有开始实现以下能力时，才增加 `campaign_rounds`：

- 应用重启后恢复尚未释放的并发 barrier；
- 回合级统一截止时间、回放、分支或恢复；
- 需要持久化 barrier 的成员到达状态。

这让 R1 保持四表，同时不给未来持久化并发挖坑。

### 5.6 最小状态机

战役状态：

> `Draft → Opening → AwaitingActions → Resolving → AwaitingActions ... → Completed`

`Paused` 可从 `Opening`、`AwaitingActions` 或 `Resolving` 进入；`Archived` 只表示从活跃列表移出，不删除事件。

单次模型生成状态：

> `Queued → Streaming → Completed`

异常分支：

> `Queued/Streaming → Stopping → Interrupted`
> `Queued/Streaming → Failed`

结束原因使用有限枚举，不把 Provider 原始错误当状态：`UserStopped`、`GlobalStop`、`Timeout`、`StreamDisconnected`、`ContextLimit`、`OutputLimit`、`RepetitionDetected`、`ProviderError`、`ProcessExited`。

只有 `Completed` 且已锁定的玩家意图能进入 GM 上下文。`Interrupted`、`Failed` 和因输出上限而不完整的内容只保留为诊断缓存。

## 6. 回合协议

### 6.1 新战役开场

1. 用户完成世界、GM、队伍和预算设置；
2. 系统保存全部快照；
3. GM 生成开场叙事和首轮行动提示；
4. 系统保存 GM 公共事件、GM-only 状态增量；
5. 战役进入“等待玩家行动”。

### 6.2 R1：三个流程预设

R1 不提供可以任意组合十几个开关的“规则编辑器”。准备大厅只给三个能直接理解的预设，内部映射为三个小字段：

| 预设 | 行动顺序 | 未裁决行动可见性 | GM 结算时机 | 适用故事 |
|---|---|---|---|---|
| **协作圆桌** | 稳定桌序，可手动再开一轮讨论 | 提交后公开 | 全员锁定后批量结算 | 共建、探索、共同穿越 |
| **秘密同投** | 稳定桌序，但语义上同时提交 | 仅自己与 GM 可见 | 全员锁定后批量结算并按规则揭示 | 狼人杀、阵营、竞争、密谋 |
| **严格先攻** | 固定编号或先攻顺序 | 默认公开，允许单次私密 | 每席位行动后立即由 GM 结算 | 战斗、追逐、严格回合制 |

内部只保存：

- `order_policy`：`TableOrder` 或 `Initiative`；
- `pending_visibility`：`Public` 或 `GmOnly`；
- `resolution_cadence`：`Batch` 或 `PerSeat`。

界面预设负责填入这三个值；R1 不向普通用户展示字段，也不创建通用流程 DSL。

三个预设共享一条硬规则：

> 当前 GM 已确认的世界事实始终冻结；尚未裁决的玩家内容只能被视为“提议”，绝不能提前写入世界状态。

因此：

- **协作圆桌**允许后发席位读取前面已经公开的提议，用后发优势换取真实协作；前面的提议仍不是已成功的事实。全桌可以由 USER 点击“再讨论一轮”，再统一锁定团队行动包；
- **秘密同投**让所有 AI 都读取同一世界快照，且不发送其他席位本轮草稿；R1 在同一冻结截止点上有限并发请求，结果仍按稳定席位顺序进入事件流。行动与其自动 `1d20` 在本轮裁定前只对提交者和 GM 可见，裁定完成进入下一轮后一起揭示；
- **严格先攻**在每个席位后立即由 GM 结算并产生新的冻结序号，下一席位看到前一席位已经公开的真实结果，而不是未裁决草稿。

批量结算的基础流程：

1. 以最后一次 GM 裁决的事件序号冻结本轮世界事实；
2. USER 填写行动并主动锁定；行动正文与系统生成的 `1d20` 在同一次事件插入中保存；
3. AI 玩家按桌序生成；其输入是否包含前序公开提议由流程预设决定；
4. 每个 AI 结果先进入自己的缓存箱，只有完整结束时才在同一次终态写入中附加 `1d20` 并锁定为有效意图；
5. 全员已锁定后才能点击“交给 GM 裁决”；技术失败席位在 R1 需要重试成功，暂不提供隐式跳过；
6. GM 一次读取有效行动集、席位所有权、冻结角色资料及各行动的可信 `1d20`，综合角色能力、方法、局势和点数进行裁决；
7. AI GM 输出必须以非空的 `【下一轮评定参考】` 最终章节收尾；缺失时本次尝试标为协议失败，原文留痕但不进入世界事实；
8. 系统原子保存公共叙事、私有投递和状态增量；
9. 当前轮号加一。

`campaign_events` 已经有 `Public`、`Private` 和 `GmOnly`，三个预设不需要新增消息系统。

### 6.3 USER 担任 GM

USER 选择“由我主持”后：

1. 准备大厅隐藏 GM Provider/模型；
2. AI 玩家根据 USER 发布的场景和行动提示作答；
3. USER 在 GM 编辑区填写公共叙事；
4. 可折叠区域提供状态增量、私有投递和下一轮参与者；
5. 点击“发布裁决并开启下一轮”后，一次性写入事件。

USER GM 不需要手写 JSON。结构化尾部由界面字段生成。

正常模式下，USER 的“GM”和“玩家”身份互斥。准备大厅可显式开启特殊模式：

> **裁判下场踢球了**

该模式允许 USER 同时拥有 GM 控制区和一个玩家席位。界面必须明确提示：

- USER 会看到 GM-only 状态，无法再保证真人玩家的未知信息体验；
- USER 玩家行动与 USER GM 裁决是两次独立提交，不能混成同一条消息；
- 玩家行动应先锁定，再开放 GM 裁决区；
- 数据层仍分别记录玩家事件和 GM 事件。

内部状态使用普通的 `GmAndPlayer` 命名；幽默名称只作为界面文案。

### 6.4 R2：同步反应

“即时反应”不应实现成多个线程同时写数据库，而应是：

1. 冻结同一个 `snapshot_sequence_no`；
2. USER 先提交并锁定行动；
3. 多个 AI 请求并发生成；
4. 每个请求只写入自己的临时结果；
5. 全部成功或达到超时后 barrier 才释放；
6. 缺席席位明确标记“本轮未行动”；
7. GM 单线程裁决并一次性提交世界变化。

并发只发生在 Provider 调用层；世界状态提交始终串行。

Grok CLI 默认最大并发应为 1。OpenRouter 等 API 可在实际验收后允许 2–4，但必须有用户可见上限，不假设订阅或 API 允许无限并发。

OpenRouter 的不同席位可以同时调用不同模型。例如 DeepSeek、Qwen、Kimi 可在同一轮读取同一个语义快照，并产生不同的策略、偏好和反应。并发结果按稳定席位顺序展示和提交，不按网络返回顺序改变角色顺序。

### 6.5 每席位独立缓存箱

缓存箱不是新的长期记忆层，也不新增表。它只是一次模型尝试在“可提交之前”的隔离区，键为：

> `campaign_id + round_no + participant_id + operation_id`

处理规则：

1. 请求开始时写入一个 `Streaming` 系统事件，并在内存中累计流式片段；
2. 不逐 chunk 写 SQLite，避免把流式频率变成数据库压力；
3. 正常结束后一次保存完整正文和 usage，进入“待锁定/已锁定”；
4. 超时、断流、重复输出、达到输出上限或手动停止时保存有限的部分正文与结束原因，但标记为 `Interrupted` 或 `Failed`；
5. 非 `Completed` 内容不发送给 GM，也不进入任何玩家的后续上下文；
6. 重试创建新的 `operation_id`，继续读取同一冻结快照，不覆盖失败尝试；
7. 应用异常退出后，重新打开时把没有终态的旧 `Streaming` 尝试收尾为 `Interrupted(ProcessExited)`。

单席位可执行的恢复动作只有：`重试`、`切换模型后重试`。R1 不自动重试，也不自动跳过，避免重复扣费或在用户不知情时缺席裁决。

## 7. 上下文组装

### 7.1 GM 上下文

按以下顺序组装：

1. 战役规则和 GM 职责；
2. GM 世界摘要；
3. 尚未合并的 GM-only 状态增量；
4. 与当前场景有关的角色快照；
5. 最近公共事件；
6. 当前轮全部玩家行动；
7. 输出协议。

### 7.2 AI 玩家上下文

按以下顺序组装：

1. 该席位角色卡快照；
2. 该席位可选导入记忆；
3. 该席位跑团专属记忆；
4. 战役公开规则的必要部分；
5. 最近公共事件；
6. 仅发给该席位的私有事件；
7. 当前 GM 行动提示；
8. “只提交意图，不裁决结果”的席位规则。

严禁加入：

- 其他玩家的私有记忆；
- 其他玩家尚未公开的本轮意图；
- GM-only 世界状态；
- 普通聊天的实时记忆引用。

### 7.3 Token 原则

不采用“所有角色卡 + 全部世界书 + 全历史”直接拼接。

MVP 暴露三个清晰预算：

- GM 历史预算；
- AI 玩家历史预算（全局默认）；
- 每次最大输出。

当上下文超限时：

- 阻止继续生成；
- 显示各部分 Token 占用；
- 允许用户生成“战役状态压缩草稿”；
- 用户保存草稿后，旧事件仍在本地，但后续上下文以确认后的摘要加近期事件为主；
- 不静默删除、截断或覆盖。

### 7.4 模型分配

模型分配属于“本次战役配置”，不新增一排全局功能分配。

准备大厅采用三层结构：

1. **简单默认**：勾选“全部 AI 使用同一模型”，只选择一次 Provider/模型；
2. **角色分工**：取消勾选后，分别选择 GM 模型和 AI 玩家默认模型；
3. **多模型阵容**：为每个 AI 玩家直接选择不同 Provider/模型；这是正式支持的体验配置，不只是故障回退。

实际选择优先级：

> 单席位覆盖 → 战役 AI 玩家默认/GM 选择 → 准备大厅从现有“角色聊天”分配中预填

预填只是减少操作；开始战役时必须解析并保存明确的 Provider、模型和参数快照。以后修改全局功能分配，不应静默改变正在进行的战役。

常见场景：

| 场景 | 所需模型设置 | 推荐 |
|---|---|---|
| USER 当 GM，只有真人玩家 | 无 | 不调用模型 |
| USER 当 GM，带 1–4 个 AI 玩家 | AI 玩家默认模型或多模型阵容 | 可让不同模型形成不同反应和倾向 |
| AI 当 GM，只有 USER 玩家 | GM 模型 | 优先可靠遵守结构化尾部、上下文较大的模型 |
| AI 当 GM，同时有 AI 玩家 | GM 模型 + 玩家默认模型 | 默认可用同一模型；控制成本时 GM 强、玩家快/便宜 |
| 全部使用 Grok CLI | 一个 Grok CLI 路由即可 | 协作/先攻按席位顺序；秘密同投可能并发，真实订阅侧并发限制尚需验收 |
| 全部使用 OpenRouter | 可统一，也可每席位不同 | 协作/先攻顺序执行；秘密同投在同一冻结轮内有限并发 |
| Grok CLI 与 OpenRouter 混用 | 分别指定 GM 和玩家默认 | 可行；准备大厅必须显示最终有效路由 |

每个席位只独立选择 Provider/模型。R1 不为每个角色再复制 temperature、top_p、上下文预算和输出上限，否则设置量会随着角色数膨胀。角色卡仍负责人物身份，多模型阵容负责增加推理路径、偏好和反应差异。

多模型阵容下，“同一轮冻结”指相同的公共事件截止点和世界事实，不代表每个模型收到完全相同的文本：各席位仍有不同角色快照和私有记忆。每个请求必须分别通过所选模型的上下文上限检查；某个模型容量不足时阻止该席位生成并提示调整或压缩，不能为了让 barrier 完成而静默裁剪。

战役进行中允许修改模型，但只影响下一次生成，并写入一条本地系统事件，保证用户知道从哪一轮开始发生变化。

## 8. GM 最小输出协议

不要求 GM 把全部叙事包进 JSON，否则流式阅读体验差且容易因一个引号破坏整轮。

推荐：

1. 正常输出可流式展示的叙事正文；
2. 末尾附一个隐藏的 `td-campaign` JSON 代码块；
3. UI 展示叙事，不展示结构化尾部；
4. 只有尾部校验成功后才能完成本轮。

最小字段示意：

```json
{
  "round": 3,
  "state_delta": "时间推进至傍晚；第七班已得知目标地点；守卫仍不知道队伍身份。",
  "private": [
    {
      "to": "participant-id",
      "text": "你认出了对方袖口上的家纹，但其他人没有注意到。"
    }
  ],
  "awaiting": [
    "user-id",
    "participant-id"
  ]
}
```

设计原则：

- 正文保持自由，不让叙事变成表格；
- `state_delta` 是简短连续性记录，不是复杂 JSON Patch；
- 私有投递明确指定收件人；
- `awaiting` 只控制下一轮参与者；
- 不自动覆盖完整世界摘要；
- 状态增量达到阈值后，沿用现有“先生成草稿、用户确认后压缩”的信任模型。

如果尾部无效：

- 已生成正文保留为待处理结果；
- 本轮不推进；
- 用户可选择“仅重试结构化尾部”或手工修正；
- 不重新付费生成整段正文，除非用户主动选择。

USER 担任 GM 时，界面直接生成上述结构化数据，不要求 USER 编写或查看协议尾部。

## 9. 界面结构

### 9.1 左侧栏

新增独立 `跑团` 入口，进入后显示：

- 最近跑团；
- 新建跑团；
- 继续、复制或归档已有跑团。

不与“聊天”列表混在一起。

### 9.2 新建跑团

使用三步设置，不建复杂向导框架：

1. **世界与 GM**：标题、世界设定、规则、开场、主持方式；选择 AI 主持时才显示 GM Provider/模型；
2. **队伍**：USER 设定、0–4 张角色卡、每张卡的记忆/原世界知识导入开关；
3. **流程与预算**：从“协作圆桌 / 秘密同投 / 严格先攻”中选择一个预设，再设置 GM/玩家历史预算、最大输出和模型覆盖预览。

开始前必须展示“本次会发送给各 Provider 的内容类别”，但不显示或读取 API Key。

### 9.3 跑团主界面

主界面使用一个明确的工作流锚点，不要求新用户自己从一组平级按钮推断下一步：

- **左侧“玩家席位”**：按稳定桌序显示 USER/AI、当前状态和席位模型。协作圆桌允许触发任意尚未行动的 AI；严格先攻只开放当前席位；秘密同投不显示逐席按钮，而在右侧用一个批量按钮按同一冻结快照生成；
- **中间“跑团记录”**：只展示不可变事件流。失败尝试继续保留，并在最新、尚未解决的失败项上提供“重试此席位”；正常完成的旧结果不允许重抽；
- **右侧“当前步骤”**：显示主持方式、USER 参与方式、当前阶段、完成进度和此刻唯一需要用户完成的动作。USER 输入、秘密同投批量生成、GM 裁定只在对应阶段出现；
- **右侧次要工具**：“额外掷骰与记录”和途中模型调整默认折叠，避免与主流程竞争注意力。界面明确说明玩家行动已自动附带 `1d20`，这里的 `NdM±K` 只创建独立公开骰点记录；

准备大厅必须显式选择：

- **我要作为玩家参与**：创建并启用 USER 席位，游玩页在轮到 USER 时显示“提交我的行动”；
- **仅观看 AI 演出**：至少选择一名 AI 玩家，游玩页隐藏 USER 输入，不再显示一个永远无法提交的文本框。

AI GM 不自动请求，也不伪装成 USER 主持。收齐有效行动后，右侧只开放“让 AI GM 裁定本回合”；USER GM 则开放“提交我的 GM 裁定”。AI GM 失败时按钮变为“重试 AI GM 裁定”，不会自动重试、自动跳过或把残缺结果当成裁定。

观察者可以点击“从下一回合加入本局”。该操作只预约一个禁用的 USER 席位；当前回合阵容保持不变，下一次完整回合边界才激活并排到稳定桌序首位。加入后不提供退出玩家席位的反向操作，避免已冻结回合中途改变参与者集合。

席位状态只需：等待、排队中、生成中、已锁定、已停止、失败/超时/输出不完整、切换模型后重试。每个席位行只显示一个当前状态；错误详情、部分输出和重试保留在事件记录中，不把主舞台变成调试面板。

当前逐席触发策略为未来“顺序发言”保留同一个席位策略入口：将来只需把可行动集合收窄为下一席位，不需要再增加一套按钮或重写持久化结构。R1 不提前开放该第四种流程。

应用顶栏在存在任何模型请求时显示红色“停止全部生成”按钮。它停止的是 TavernDesk 当前登记的聊天、记忆和跑团生成，不是“断开 API 账号”：

- 点击后按钮禁用，状态改为“正在停止 N 项…”；
- 完成后显示“已停止 N 项生成；部分输出未提交”；
- 没有活动请求时隐藏按钮，不常驻一个容易误触的红色控件；
- 不弹确认框，因为异常死循环时停止速度比二次确认更重要。

### 9.4 按钮帮助

所有按钮（包括当前禁用的按钮）悬停 2 秒后显示小型半透明说明框：

- 可用按钮说明执行结果和适用阶段；
- 禁用按钮说明尚缺少的输入、席位或阶段条件；
- 帮助框不承担关键错误提示；请求失败和持久化失败仍在页面状态与事件流中明确显示。

### 9.5 导演视角

用户是本地数据所有者，应可主动切换到“导演视角”查看 GM-only 状态和每个角色私有信息。

普通游玩视角默认隐藏这些内容，避免用户无意中剧透。是否允许随时查看，需要用户最终确认。

## 10. 故障与一致性

必须覆盖：

- 秘密同投的所有 AI 请求绑定相同冻结序号；
- 协作圆桌只允许读取前序公开提议，不把它们当成世界事实；
- 严格先攻必须在上一席位裁决完成后才开放下一席位；
- 同一玩家/同一轮不得重复提交生效；
- GM 裁决使用 `campaign_id + round_no + operation_id` 幂等；
- 取消某个 AI 只取消该席位，不删除其他已提交行动；
- 关闭页面不取消后台请求，退出应用才统一收尾；
- Provider 超时后由用户显式重试或换模型后重试，不自动重复扣费；
- 达到输出上限、流式错误或疑似重复死循环的结果不自动锁定；
- 世界状态版本不匹配时拒绝提交旧裁决；
- 私有事件查询必须同时匹配 `campaign_id` 和 `recipient_id`；
- FTS 或普通聊天检索默认完全不索引跑团私有/GM-only 内容。

### 10.1 复用一个应用级生成主管

当前聊天已经有应用级生成协调器。实现跑团时应把它收敛为一个轻量的生成主管，而不是再建第二个任务框架。每项活动生成只登记：

- `scope`：`Chat`、`CampaignSeat`、`CampaignGm` 或 `Memory`；
- `scope_id`；
- `operation_id`；
- 当前状态、取消源与结束原因。

现有聊天接口可保留为包装层。只有聊天、跑团 GM、跑团席位和记忆生成都登记后，顶栏按钮才可以真实命名为“停止全部生成”；如果某条调用链尚未纳入，界面必须缩小文案范围，不能虚报。

全局停止顺序：

1. 暂时关闭新操作登记入口，并取得当前活动操作快照；
2. 把每项操作转为 `Stopping` 并发出取消；
3. HTTP/SSE Provider 取消并释放响应流；本地统一记为 `Interrupted(GlobalStop)`；
4. Grok CLI ACP 先发送会话取消；短暂宽限后仍未结束，才关闭 stdin 并终止该次隔离进程；
5. 以 `operation_id` 和终态守卫忽略迟到 chunk；
6. 保存有限部分输出作为诊断，但不提交为消息、记忆或玩家行动；
7. 所有已登记操作收尾后重新开放新请求。

HTTP Provider 没有通用的“把结束状态回传给模型”协议。正确语义是关闭客户端流，再由 TavernDesk 保存明确的本地终态；OpenRouter 也说明取消流是中止连接，能否立即停止上游计算和计费取决于实际 Provider。参考：

- <https://openrouter.ai/docs/api/reference/streaming>
- <https://ai-sdk.dev/docs/advanced/stopping-streams>
- <https://agentclientprotocol.com/rfds/request-cancellation>

完成与停止同时发生时只允许一个终态胜出；一旦终态写入，任何迟到事件都不得再改变缓存箱或推进回合。

### 10.2 输出健康守卫

健康守卫放在 Infrastructure 已经归一化的流之后、App 缓存之前，只检查会被保存和进入上下文的正文。reasoning 原文不会越过 Provider 边界；其资源风险由输出上限、取消令牌和顶栏全局停止兜底，避免为不可见内容再建设第二套缓存。

R1 只做保守、可解释的精确重复检测，不做语义相似模型：

- 至少接收 128 个字符后才启用；
- 1–8 个有效字符的短单元连续重复 16 次；
- 24–256 个字符的块连续重复 4 次；
- 仅统一行尾和连续空白，不改写正文；
- 只保存 512–1024 字符滚动窗口，不复制完整输出。

命中后只停止该操作，结束原因为 `RepetitionDetected`，部分输出留在缓存箱，用户可重试或换模型后重试。最大输出上限、首字超时和流中断仍是第一层防线；红色全局停止按钮是人工兜底。

### 10.3 反证清单

并发和流式模式最容易发生的错误：

1. 某个玩家读到更新后的同轮内容；
2. 部分玩家失败但 GM 当成完整行动集；
3. 私有记忆串入另一个玩家；
4. 旧 GM 裁决覆盖新状态；
5. 重试产生重复行动或重复计费。
6. 全局停止时新请求逃出登记表；
7. 已中止操作的迟到 chunk 把状态改回完成；
8. ACP 已取消但子进程仍继续输出。

防线不是提示词，而是冻结序号、唯一操作 ID、单写提交、终态守卫和查询过滤。

## 11. 分阶段实施

### R1：独立跑团闭环（已实现）

已实现：

- 左侧独立入口；
- 剧本库、新建/继续跑团和同一剧本另开一局；
- GM + USER + 0–4 个 AI 玩家；`1 GM + USER + 0 AI` 是有效的最小阵容；
- 角色卡/Persona/可选记忆快照；
- 一张剧本模板表与三张独立跑团表；
- GM 开场、玩家行动、GM 裁决；
- 协作圆桌、秘密同投、严格先攻三个流程预设；
- 协作/先攻顺序生成、秘密同投冻结快照并发、世界事实冻结、手动推进；
- 公共/私有/GM-only 可见性；
- 每席位独立缓存、停止、重试和恢复；
- Token 检查、输出不完整识别与保守重复检测；
- 应用顶栏“停止全部生成”和统一终态；
- 游戏途中单席与 GM 模型路由变更；
- 每条成功玩家行动原子附加可信 `1d20`，并以结构化 JSON 和显性正文同时留痕；
- `NdM±K` 额外公开骰子与独立事件留痕；
- GM 上下文显式提供玩家席位所有权与冻结角色/Persona 资料；
- GM 可推进世界、NPC 与剧情，但不能替玩家新增台词、心理、决定、反应或下一步；
- AI GM 的 `【下一轮评定参考】` 收尾协议、失败留痕与显式重试；
- 秘密同投的行动及自动骰在裁定前互盲、裁定后一起揭示；
- 起始大厅显式选择 USER 参与或仅观看 AI 演出；
- 右侧“当前步骤”驱动 USER、逐席 AI、秘密同投和 GM 裁定；
- AI GM 只在用户点击“让 AI GM 裁定本回合”后调用；
- 观察者可预约从下一完整回合加入，当前回合阵容不变；
- 所有按钮在悬停 2 秒后显示帮助，禁用按钮解释未满足条件；
- 普通聊天零回写。

明确排除：

- 自动无限跑团；
- 完整规则骰子引擎；
- 角色属性面板、背包、地图和战斗棋盘；
- 向量数据库；
- NPC 独立模型；
- 语音；
- 通用 Agent 编排框架；
- 本地模型/Ollama。

### R2：长局验证后再决定

- 可恢复的持久化 barrier、统一回合截止时间和跳过策略；
- Provider 并发上限；
- 必要时新增 `campaign_rounds`。

### R3：经使用验证后再决定

候选：

- 角色属性、物品与任务；
- 战役分支/回滚；
- 世界包导入导出；
- 跑团记忆合并草稿；
- 地图或附件。

没有真实使用需求时，不建设这些能力。

## 12. MVP 验收标准

1. 用雪乃、海梦创建火影跑团后，两张原角色卡和普通记忆保持原样。
2. 关闭记忆导入时，AI 玩家请求不包含普通聊天记忆。
3. 开启导入后，跑团只读取创建时快照；后续编辑普通记忆不影响跑团。
4. AI 玩家 A 的上下文不含 B 的私有事件、私有记忆或 GM-only 状态。
5. 秘密同投中所有 AI 读取相同冻结序号，且请求不含其他席位本轮草稿。
6. 协作圆桌中后序席位能读取已公开提议，但提示中明确它们尚未被 GM 裁定。
7. 严格先攻中，下一席位只能读取上一席位已经由 GM 保存的裁决。
8. GM 只裁决一次；重试不会重复写入生效行动或状态增量。
9. 某个 AI 超时、断流、达到输出上限或重复输出后，部分正文保留在该席位缓存箱，但不进入 GM 上下文；可重试或换模型后重试，其他行动不丢失。
10. 页面关闭后后台生成继续；重新进入可以附着当前状态。
11. 上下文超限时阻止生成并说明占用，不静默截断。
12. 顶栏停止全部生成后，聊天、记忆和跑团的已登记请求均进入明确终态；迟到 chunk 不会创建消息、覆盖记忆或锁定玩家行动。
13. Grok CLI 使用现有隔离 ACP 路径；API Provider 不出现专用条件分支进入 App。
14. 观察模式不显示 USER 输入；预约加入后只在下一完整回合激活 USER 席位。
15. AI GM 不自动调用；只有行动集就绪且用户明确点击后才请求裁定，失败时必须显式重试。
16. 协作圆桌可逐个触发任意尚未行动的 AI，严格先攻只开放当前席位，秘密同投保留一次批量并发入口。
17. 所有按钮（含禁用状态）悬停 2 秒后显示用途或禁用原因。
18. USER 与 AI 的每条成功锁定行动都以同一原子写入附加一个 `1d20`，点数为 `1–20`，正文末尾与结构化数据一致；失败或中断的 AI 行动不生成行动骰。
19. GM 请求包含全部启用席位的所有权声明、USER Persona/角色冻结快照及本轮每条有效行动的自动骰；玩家模型被明确禁止自行伪造骰点。
20. `1`/`20` 只表示强烈负面/正面倾向，不是绝对失败/成功；纯对话和低风险行动不得因低点数被抹除，点数可转而影响反应、机会、细节或局势。
21. AI GM 缺少非空 `【下一轮评定参考】` 时，本次输出标记为协议失败且不锁定、不推进回合；原文和尝试链保留，重试成功后才进入下一轮。
22. GM 可以描述已提交行动如何展开并引入剧情、环境、NPC 和旁白，但不得替玩家补写新的台词、心理、选择、反应或下一步行动。

## 13. 规则决定

### 已确认

1. **行动可见性由故事决定**
   准备大厅选择“协作圆桌 / 秘密同投 / 严格先攻”；协作允许参与者看到彼此尚未裁决的公开提议，竞争模式互盲，严格顺序逐席位裁决。允许单次私密行动时仍使用现有 `Private` 事件，不增加第四个流程模式。

2. **USER 可当玩家，也可当 GM**
   正常情况下两者互斥；可显式开启“裁判下场踢球了”模式同时兼任。USER 当 GM 时不调用 GM 模型，通过界面提交叙事、状态增量和私有投递。

3. **记忆导入默认值**
   角色卡必做快照；普通角色记忆、Persona 记忆和原世界知识默认关闭，在开局准备大厅逐项选择。

4. **GM 对私有记忆的权限**
   GM 可读取所有参与者的跑团快照和私有事件；AI GM 模式下，这些内容会发送给所选 GM Provider。

5. **状态增量提交**
   每轮 GM 状态增量自动保存为不可变事件；只有压缩成世界摘要时需要用户确认。

6. **导演视角**
   用户可随时查看，默认折叠并提示剧透。

7. **战役本地模型分配与多模型阵容**
   默认可让全部 AI 使用同一模型；也允许为 GM 和每个 AI 玩家选择不同模型。协作圆桌与严格先攻按席位顺序执行，秘密同投基于同一轮冻结快照有限并发。USER 当 GM 时只显示 AI 玩家模型。不新增五种全局功能分配。

8. **三种流程预设**
   协作故事使用“协作圆桌”，允许后序参与者看到并配合前序公开提议；竞争和隐藏身份故事使用“秘密同投”，所有行动互盲后由 GM 统一裁决；需要严格顺序时使用“严格先攻”，每席位结算后再进入下一席位。

9. **每席位独立缓存与技术失败重试**
   每个 AI 本轮结果先进入独立缓存箱。超限截断、断流、超时和疑似重复死循环都不送给 GM；用户可以重试或换模型后重试，其他席位结果不丢失。

10. **应用级紧急停止**
    顶栏活动请求状态旁提供红色“停止全部生成”；停止后 TavernDesk 保存本地中止状态和有限部分输出，不把中止伪装成 Provider 已正常完成。

11. **AI GM 由用户明确触发**
    AI GM 不随玩家行动完成自动请求。有效行动全部就绪后，用户点击“让 AI GM 裁定本回合”；失败后必须重试或切换模型，不允许跳过。

12. **USER 参与方式与途中加入**
    AI GM 跑团在大厅明确选择“我要作为玩家参与”或“仅观看 AI 演出”。观察者不显示 USER 输入，可单向预约从下一完整回合加入；当前回合不改变阵容。

13. **逐席操作为顺序发言预留策略入口**
    协作圆桌允许任意未行动 AI，严格先攻只允许当前席位，秘密同投仍以同一冻结快照批量生成。未来顺序发言只需把可行动集合收窄为下一席位，R1 不新增第四种预设。

14. **按钮帮助覆盖禁用状态**
    所有按钮悬停 2 秒后显示简短半透明说明；禁用按钮必须直接说明缺少的条件，不能只靠灰色状态让用户猜测。

15. **玩家行动自动附带统一 `1d20`**
    USER 与 AI 的每条完整行动在锁定时由系统生成一枚真实 `1d20`，显示在行动正文最后并保存结构化数据。骰点与行动共用可见性和同一次数据库终态写入，不能出现“行动已保存但骰点缺失”的半状态。

16. **骰点是情境倾向，不是固定成功表**
    GM 同时考虑角色能力、方法、既有事实、风险与点数。高低点提供正负倾向，`1`/`20` 也不推翻世界可行性；对已说出的台词或安全行动，低点只能影响外界反应、机会、细节或后续局势。额外 `NdM±K` 工具不替代行动自动骰。

17. **GM 世界权与玩家自主权分离**
    GM 拥有世界、环境、NPC、情报和后果裁定权，可以引入新剧情与旁白；PlayerIntent 是玩家已经授权的完整选择，GM 不得继续替玩家生成新台词、心理、决定、反应或下一步。每次 GM 发言以 `【下一轮评定参考】` 说明灵活的风险、机会和裁定因素，不规定必选路线、技能、台词或反应；AI GM 缺失该章节时必须显式重试。

### 可以延后到 R2

11. 同步反应中 USER 是先提交再看 AI 输出，还是与 AI 同时提交？
12. 某个 AI 超时时默认等待、跳过，还是暂停并询问？
13. 并发响应是到达即显示，还是全部完成后一起揭示？
14. Grok CLI 是否永远串行，还是允许用户主动提高并发并承担订阅侧限制？

### 可以延后到 R3

15. 是否需要角色数值、背包、任务和时间线面板？
16. 是否允许把跑团经历生成合并草稿带回角色普通记忆？
17. 是否需要战役分支、回滚和世界包分享？

### R1 已采用的剩余决定

1. **自动行动骰与额外骰子工具已加入**
   每条完整玩家行动自动附带统一 `1d20`；另有只解析 `NdM±K` 的额外公开骰点工具。两者都不扩展为属性、技能、战斗或规则书引擎。

2. **正常完成的 AI 行动自动锁定**
   技术失败、断流、超限、停止或重复输出可创建新尝试；旧尝试作为不可变诊断保留，正常完成内容不因主观不喜欢而反复重抽。

## 14. 推荐的下一步

R1 已形成闭环，不建议继续铺设通用规则框架。下一步按真实使用证据排序：

1. 先用短局和一次中等长度真实跑团验证三种流程、上下文预算、途中换模型与失败重试；
2. 收集不同 Provider 的首字超时、流中断、输出上限和并发限制，不提前建设服务商特例矩阵；
3. 只有真实长局出现“世界摘要过长”时，再设计用户确认的跑团摘要压缩；
4. 只有用户确实需要跨进程恢复同轮并发时，才新增 `campaign_rounds` 与持久化 barrier；
5. 属性、背包、地图、战斗棋盘、分支回滚和跑团记忆带回角色继续保留为 R3 候选，不因功能看起来完整而提前实现。
